01about

왜 만들었나

예금 해지와 대출 중 무엇이 유리한지, 비교가 어려운 이유입니다.

사용자가 마주하는 상황

갑작스럽게 목돈이 필요해진 상황. 만기 7개월 남은 예금을 깨면 쌓아둔 이자를 대부분 잃고, 대출을 받으면 이자를 새로 냅니다.

어느 쪽이 나은지 알려면 중도해지 이율, 남은 기간, 대출금리, 중도상환수수료를 다 따져봐야 합니다. 낯선 용어투성이라 어디서부터 비교해야 할지도 막막합니다. 결국 감으로 정하거나 은행 창구에 묻게 됩니다.

서비스가 하는 일

보유 예금과 필요 금액만 입력하면, 두 선택지의 총비용을 같은 시점 · 같은 세후 기준으로 환산해 비교합니다.

해지가 유리하면 해지하라고 말합니다. 상품을 파는 계산기가 아니라, 사용자가 스스로 판단할 근거를 주는 것을 목표로 했습니다.

07data pipeline

데이터 파이프라인

신용대출과 전세대출 데이터의 크롤링 과정입니다.

단계 하는 일
00
수집원
  • 신용대출 : 동적 렌더링 방식 → Playwright로 브라우저 실행 후 대출신청자격, 금리 및 이율이 표시된 시점의 HTML 수집
  • 전세대출 : 완성된 정적 HTML → Jsoup으로 직접 요청해 수집
  • 두 크롤러 모두 상품 상세 주소 단위로 수집하고, 파싱은 공통으로 Jsoup 사용
01
배치 시작
  • crawling_batch_history 생성, 배치 UUID·은행명·상품 구분·시작 시각·실행자를 함께 저장하고 상태를 RUNNING으로 기록
  • 배치 이력은 별도 트랜잭션으로 즉시 커밋하여 후속 작업 실패 시에도 기록 보존
02
크롤링 · 파싱
  • 공통으로 Jsoup을 사용해 상품 정보 · 금리표 · 우대조건 파싱
  • 신용대출은 공시 API 데이터를 반영해 신용등급별 금리로 환산
03
이력 저장
  • SHA-256 지문을 생성해 직전 값과 비교, 변경 없으면 저장 생략
  • 변경 시 상품 이력과 금리 이력을 함께 하나의 트랜잭션으로 커밋
04
라이브 반영
  • 상품은 상품명, 금리는 (상품 · 금리주기 · 신용등급) 기준으로 UPDATE 또는 INSERT
  • 우대 · 자격조건은 미등록시에만 추가
  • 전체 작업은 하나의 트랜잭션으로 처리해 실패 시 모두 롤백
05
배치 마무리
  • 대상 · 성공 건수와 라이브 반영 여부를 SUCCESS / PARTIAL / FAILED 중 하나로 확정

09troubleshooting

트러블슈팅

실제로 겪은 문제입니다.

금리와 상환기간의 상호 의존 문제 발생

problem

대출금리는 3개월·6개월·12개월 중 어떤 주기를 선택하느냐에 따라 달라집니다.
근데 어떤 주기가 맞는지 알려면 실제로 몇 개월 만에 다 갚는지 먼저 알아야 하고, 그 상환 개월수를 계산하려면 금리가 먼저 있어야 합니다.
닭이 먼저냐 달걀이 먼저냐 같은 상황이라, 잘못 고르면 사용자한테 실제보다 비싼 금리가 보이는 문제였습니다.

approach

두 가지 방법을 써봤습니다.
① 예금이 얼마나 남았는지 보고 금리 주기를 미리 짐작하는 방법, ② 제일 짧은 주기부터 하나씩 대입해보면서 맞는 걸 찾는 방법.
①번은 문제가 있었습니다 — 사용자가 일찍 다 갚아버리면, 미리 짐작했던 주기가 실제보다 길게 잡혀서, 원래보다 비싼 금리가 선택돼 버렸습니다. 

int ratePeriod = 3;                                // 가장 유리한 주기부터
while (true) {
    BigDecimal rate = ratesByPeriod.get(ratePeriod);

    // 월납입만으로 상환 시뮬레이션 (만기 목돈 상환 없음)
    LoanSimulator.Result r = LoanSimulator.simulateMonthlyOnly(loanAmount, rate, monthlyPayment);

    if (r.repaymentMonths() <= ratePeriod || ratePeriod == 12) {
        return new Resolution(ratePeriod, rate, ...);  // 금리·상환개월 동시 확정
    }
    ratePeriod = nextRatePeriod(ratePeriod);          // 3 → 6 → 12
}
선택 이유 — 짧은 주기일수록 금리가 낮으므로, 3개월부터 올라가면 처음 조건에 맞는 주기가 곧 가장 낮은 금리입니다.
BigDecimalPMT순환 의존성

result

금리와 실제 상환 개월 수가 한 번에 같이 정해집니다. 일찍 다 갚든 12개월을 넘기든, 조건에 맞는 가장 짧은 주기가 잡혀서 사용자가 받을 수 있는 제일 낮은 금리가 나옵니다.

계산 불가→3·6·12개월 중 상환 가능한 최단 주기 선택

단, 12개월 안에도 다 갚지 못하면 최장 금리변동주기인 12개월로 확정됩니다.

테스트 만기에 목돈으로 갚는 경우와 아닌 경우, 금리 주기 3가지를 모두 조합해서 단위 테스트로 검증했습니다. 직접 손으로 계산한 명세서 4건과 비교해봤고, 전부 일치했습니다.

실제 비교 결과 화면 — 대출금리가 연 5.21%(12개월)로 확정됐습니다

lesson learned

처음엔 이걸 수학 공식처럼 한 번에 풀려고 하다가 막혔습니다. 근데 생각해보니 은행이 제공하는 금리 주기는 3개월·6개월·12개월, 딱 세 가지뿐이었습니다. 무한히 어려운 문제가 아니라, 세 개 중에 고르면 되는 문제로 바뀌었습니다. 기술로 풀기 전에, 먼저 실제 상황을 제대로 봤어야 했습니다.

10feedback

피드백과 개선

멘토 피드백 대응
전태경 계좌번호가 평문으로 저장된다 AES-256-GCM 암호화. 키는 환경변수에 두어 DB 접근만으로는 복호화할 수 없게 함
전태경 크롤링이 실패하거나 두 번 실행됐을 때 어떻게 되는지 불명확하다 배치 이력 테이블 + 스냅샷 해시 + 복합 UNIQUE 3중 방어. 49회 실행에 중복 0건
전태경 운영자가 금리 변경 시점을 알 수 없고, 계산 결과도 남지 않는다 이력 테이블 5개 신설, 비교 결과는 계산 시점의 금리·한도를 복사해 보관
전태경 금융 계산에 자바 double을 쓰면 오차가 생길 수 있다 BigDecimal 전면 적용. 중간 정밀도 20자리, 반올림은 최종 1회
지석호 예금삭제·로그아웃 alert이 화면마다 다르다 Composable + 공통 모달로 통일
조용훈 API 명세서 없이 프론트·백엔드가 각자 다르게 개발하고 있다 엔드포인트 29개 명세 작성 후 양쪽이 같은 문서를 참조
자체 발견 탈퇴한 이메일로 다시 가입할 수 없다 탈퇴 시 이메일을 익명화해 UNIQUE 자리를 비움. 물리 삭제하면 비교 이력까지 사라지고, 그대로 두면 재가입이 막히는데 익명화가 둘을 동시에 해결
11open issues

보완 계획

  • 히스토리 테이블 조회 기능 없음 — 상품·금리 변경과 예금 수정 이력은 히스토리 테이블 5개에 정상적으로 쌓이고 있지만, 이를 조회할 API와 화면이 없어 현재는 DB에 직접 접속해야 확인할 수 있습니다.
  • OCR 동기 처리 — 인식이 5~10초 걸리는 동안 톰캣 스레드를 점유합니다. 처리 ID를 먼저 발급하고 폴링으로 조회하는 방식으로 바꿔야 합니다. 전태경 멘토
  • 상품 코드 체계 도입 — 현업은 대·중·소분류 코드로 상품을 나눕니다. 상품명도 별도 테이블로 분리해야 합니다. 지석호 멘토
